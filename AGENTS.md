# AGENTS.md

Onboarding doc for any agent (or human) picking up **this directory** cold. If you're reading
this on Prajna, this directory *is* `PROJECT_ROOT` (`~/pcb` by default — see
`.claude/PRAJNA_CONFIG.md` §1). If you're reading it anywhere else, it's a staged copy of that
same payload, about to be (or just) `rsync`'d over.

## What this project is

PCBA (assembled PCB) defect detection — training defect detectors on an annotated dataset,
progressing YOLO11s → RT-DETR → GMO-DETR (a from-scratch reimplementation; no official code was
released for it). This directory holds everything a training run needs: the four scripts, the
dataset, and the Prajna skillset that knows how to run them on this cluster.

**What's deliberately *not* here**: `README.md` (full project narrative + results tables),
`PCB_Defect_Detection_Full.pptx`, and the `imaging-front-end/` optics docs. Those live in the
origin git repo (`PCB_defect_detection_internship/`, one level up from this directory's
counterpart on the dev machine) and aren't needed to run a training job — they weren't copied
over. If you need the results narrative for context (e.g. the noise floor, published baselines),
ask the user to paste the relevant section rather than assuming it's on disk here.

`offline/`, `runs/`, `logs/` don't exist yet at a fresh checkout — `prajna-env` creates and

jobs actually run. See `PRAJNA_CONFIG.md` §8 for exactly what goes where and why.

**12 classes** (counts in `categories/`): Component Crack (6), Component Damage (11), Component
Liftup (22), Component Missing (43), Component No Solder (68), Component Solder Dry (133), LED
Damage (7), Polarity Wrong (36), RYB Wrong Sequence (24), Solder Ball (34), Solder Short (152),
Tombstone (15).

The **8-class study** (`8classes_kfold.py`, `rtdetr.py`) drops the four rarest (Component Crack,
Component Damage, LED Damage, Tombstone — all ≤15 instances) and keeps: Component Liftup,
Component Missing, Component No Solder, Component Solder Dry, Polarity Wrong, RYB Wrong
Sequence, Solder Ball, Solder Short.

## Important: the four scripts were written for Kaggle, not this cluster

All four `.py` files are Colab/Kaggle notebook exports (`# Automatically generated by Colab`)
and hardcode Kaggle input paths at the top, e.g.:

```python
INPUT_ROOT     = Path("/kaggle/input")
WORK           = Path("/kaggle/working")
YOUR_COCO_JSON = "/kaggle/input/datasets/vidishagar/pcb-large-coco/annotations/instances_default.json"
YOUR_IMG_ROOT  = "/kaggle/input/datasets/vidishagar/pcb-large-dataset/categories"
NEG_IMG_ROOT   = "/kaggle/input/datasets/vidishagar/non-def/non-def"   # or non-def-1200/... in rtdetr.py
```

None of these paths exist here. Don't hand-patch them — use `.claude/skills/pcb-port-to-batch/`:
copy its `assets/hpc_env.py` next to the script being ported and import its path constants
(`COCO_JSON`, `IMG_ROOT`, `NEG_ROOT`, `WEIGHTS_DIR`, `RUNS_ROOT`, `devices()`) in place of the
Kaggle block. `hpc_env.py` already resolves `DATA_ROOT` to `PROJECT_ROOT/data/pcb_all_work` —
exactly this directory's `data/pcb_all_work/` — so no manual path table is needed once a script
is ported this way. That skill also covers the other Kaggle-specific issues: `device=[0,1]`
(dual-GPU, wrong for this project's scale), `!pip install ...` magic cells, and
`gmo_detr_full_pipeline.py`'s relative-path YAML write.

`pretrain_soldef_yolo.py` additionally depends on a **SolDef_AI `Labeled/` folder that is not
present anywhere in this directory**. That script is blocked until that external dataset is
sourced separately (it's the public SolDef_AI dataset, not part of `pcb_all_work`) — check
`PRAJNA_CONFIG.md` §7 for current status before assuming it's been resolved.

## Script-by-script summary

- **`8classes_kfold.py`** — YOLO11s on the 8-class subset. Builds YOLO-format data from COCO +
  negatives with a stratified (rarest-class-aware) split, trains a 640px baseline, sweeps
  960/1280px, then runs 5-fold stratified CV.
- **`rtdetr.py`** — Same 8-class data pipeline and split logic as above, trained with
  Ultralytics `RTDETR` (`rtdetr-l`, HGNetv2 backbone) instead of YOLO.
- **`pretrain_soldef_yolo.py`** — Builds a YOLO dataset from the SolDef_AI solder-defect
  dataset (LabelMe JSON → COCO → YOLO), pretrains YOLO11s on it, then fine-tunes two arms (A:
  ImageNet/COCO init, B: SolDef_AI-pretrained init) on this project's data and compares —
  including a no-negatives ablation and EigenCAM visualizations. **Blocked** — see above.
- **`gmo_detr_full_pipeline.py`** — Implements GMO-DETR from scratch (GhostConv stem,
  DMambaOut/GatedCNN backbone, CAFF neck with CAA attention, GSConv, TAIFI/TSSA replacing
  AIFI's self-attention), registers the custom modules into Ultralytics' `RTDETR` framework via
  a patched `parse_model`, assembles the model from a hand-written YAML, sanity-checks it
  (shape/param/gradient/overfit tests), then trains on the full 12-class dataset for 200 epochs.

## Working conventions

- **Read `.claude/PRAJNA_CONFIG.md` before doing anything cluster-specific.** It holds every
  site- and project-specific value (partitions, QOS, quotas, paths) the skills reference, and
  wins over any skill file if the two disagree — it reflects what was actually observed on the
  cluster, not what was assumed when the skill was written.
- **Never run training directly on the login node** — it gets killed. Environment setup is fine
  there; training goes through `sbatch`/`salloc`/`srun` (`prajna-jobs`).
- The `.py` files are notebook exports, not CLI tools — top-to-bottom module-level code, no
  `if __name__ == "__main__"`, no argparse. Keep any port mechanical (smallest diff that runs
  unattended) rather than restructuring, per `pcb-port-to-batch/SKILL.md`'s explicit philosophy
  — unless the user asks for more than a working port.
- **This directory has a counterpart on the original dev (Windows) machine**, nested inside a
  git repo at `PCB_defect_detection_internship/pcb/`, where `data/`, `runs/`, `logs/`,
  `offline/` are gitignored. If you edit scripts or skills here on the cluster, those edits are
  local to Prajna until someone manually `rsync`s them back — no automatic sync exists in either
  direction.
- If something surprising happens on this cluster that isn't in `PRAJNA_CONFIG.md` §10's
  observed-behaviour log, add it there (with a date) before moving on — that's what keeps the
  next session from rediscovering it.
